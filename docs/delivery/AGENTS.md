# 三命无常项目强制工作指令

对本目录及其所有子目录执行任何与美术、UI、HTML视觉原型、角色、场景、图标、按钮、字体、动效、VFX、视觉评审或交付验收有关的任务时，必须：

1. 使用 `sanming-art-director` 技能。
2. 完整读取 `三命无常_美术总监工作手册_v1.md` 后再采取任务行动。
3. 将 Gate A 方向、Gate B 系统、Gate C 状态、Gate D 像素、Gate E 视口、Gate F 交付加入当前工作计划。
4. 以最终运行画面为准，不以CSS数值、DOM矩形或孤立素材代替成图验收。
5. 复现用户指出的精确交互状态后再判断根因；发现一项缺陷时递归检查同类组件和相关状态。
6. 默认检查桌面基准、紧凑桌面、用户当前/窄视口，以及默认、悬停、按下、选中、焦点、快速切换状态。
7. 对争议组件执行100%全图、400%完整边缘和800%角落/接缝检查。
8. 源文件与独立版必须同步；图片加载错误与控制台错误必须为0。
9. 连续两轮扩展检查均未发现新问题，才允许标记“可交付”。
10. 每次交付必须附工作手册规定的六道门禁记录和截图证据；任何门禁未通过，必须继续修改并明确标记“不可交付”。

不得用“顶级”“已全部检查”“无问题”等主观结论替代证据，不得让用户承担本地可完成的基础质量检查。

## Codex 项目总控规则

每个新任务开始时，还必须读取：

1. `00_用户只看这里_项目总控.md`
2. `PROJECT_STATE.md`
3. `CURRENT_TASK.md`
4. `CODEX_TEAM_OPERATING_SYSTEM.md`
5. `MODEL_ROUTING.md`

执行约束：

1. 用户只需要描述目标、问题或说“继续”；总控 Agent 负责判断岗位、拆出一个当前工作包并更新 `CURRENT_TASK.md`，不得要求用户自己拆任务或复制代码。
2. 同一时刻只有一个主要工作包处于“进行中”。没有用户明确授权，不并行修改同一组源文件。
3. 日常缺陷只做精确复现、最小修复和关联回归；只有模块里程碑或正式交付才执行完整 Gate A–F 与两轮扩展检查。
4. 发现旁支问题时记录到 `PROJECT_STATE.md` 的候选队列，不得自动扩展当前修改范围。
5. 当前工程真源默认为 `prototype/play/index.html`、`game.css`、`delivery-v2.css`、`game.js`；独立版 `prototype/play/三命无常_V1完整交付.html` 由 `build-delivery.mjs` 生成。若实际情况改变，必须先更新 `PROJECT_STATE.md`。
6. 连续两次修复未解决、连续三次工具/连接失败、上下文压缩后目标不清、或预计修改超出当前工作包时，立即停止继续消耗，写清证据并把任务标记为“需要接管”。
7. 每次任务结束必须更新 `PROJECT_STATE.md` 和 `CURRENT_TASK.md`，让新对话无需依赖旧聊天记录即可接管。
8. 不把 Git 初始化、提交、删除、覆盖历史版本等操作夹带在产品任务中；此类基础设施操作必须成为单独工作包。

## 自动派单授权

用户已明确授权项目总控按需自动创建、监控和协调新的 Codex 任务，用户不需要手工新建岗位窗口。

1. 总控可为边界清楚的程序、美术、QA、发布或只读调查工作自动创建任务。
2. 自动创建前必须把岗位、目标、允许写入范围、验收标准和停止条件写入任务提示；新任务必须读取本目录的项目规则与状态文件。
3. 当前采用效率优先模式：默认允许两个独立岗位任务并行；能证明文件、状态和构建互不冲突时最多三个并行。
4. 只有互不依赖且不写同一文件的工作才允许并行。同一个文件族保持单写入者；不同模块、不同文件族可以并行。独立版构建仍是单通道，构建时不得同时修改其真源输入。
5. 总控负责等待岗位结果、判断是否需要追问、把结果写回项目状态，并向用户给出一次汇总；不得要求用户在多个任务间传话。
6. 完成或被取代的岗位任务由总控归档；需要用户做实质方向裁决的任务保留并明确提示。
7. 不为“常驻岗位”空开任务。只有存在具体工作包时才创建对应岗位任务，以控制算力消耗。
8. 创建岗位任务时必须按照 `MODEL_ROUTING.md` 显式指定模型与推理档位，并在任务提示中写明；不得沿用不确定的默认模型。
9. 岗位任务不得自行提高模型或推理档位。只有总控核实满足升级条件后，才允许创建升级任务或在下一轮切换配置。
10. `xhigh`、`max`、`ultra` 默认禁用；除非用户明确要求或 `MODEL_ROUTING.md` 规定的正式交付升级条件成立。

## 审计后自动修复授权

用户已明确授权：对已经纳入当前工作包或当前模块审计范围的缺陷，Agent在复现并取得证据后直接进入修复、构建和复测，不再等待用户重复说“请修复”。

1. 总控负责把审计发现登记为工作包，并自动派唯一写入岗位。
2. 修复范围仅限已确认缺陷及直接关联状态；重大玩法规则、美术方向或不可逆数据变更仍需用户裁决。
3. 只读审计可并行；写入任务继续遵守文件所有权和构建单通道规则。
4. 修复后必须自动回到QA；失败继续迭代或按停止条件上报，不把基础复测交给用户。

## 用户可见工作组与总控纠错规则

以下规则来自实际协作复盘，优先级与“自动派单授权”相同：

1. 用户所说的“多窗口、小弟、岗位任务”默认指 Codex 侧边栏中可见、可独立打开的任务。后台子代理只允许处理短时、内部、无需用户查看的子步骤，不得冒充用户要求的可见岗位窗口。
2. 项目总控是用户唯一需要持续沟通的窗口。总控不得亲自包揽本应派给程序、真源、QA或视觉岗位的大工作包；总控只负责拆包、创建可见任务、监控、收回结果、继续派修和最终裁决。
3. 当用户已经授权自动派单时，发现明确且在当前模块范围内的缺陷后，必须在同一轮完成“登记缺陷 → 创建或续派唯一写入任务 → 安排只读复测任务”。不得只汇报问题清单后停下等待用户再次说“开始”或“修复”。
4. 不得在没有工具状态证据时说“已经开始”。宣称开始前必须至少满足一项：任务创建成功并返回 `threadId`；已有任务快照显示 `active/inProgress`；或实现任务已产生可核验文件/命令进度。创建空窗口、只写计划或发送提示不算开始。
5. 创建可见岗位任务后，总控必须向用户展示创建结果；后续由总控用任务快照跟踪，不要求用户进入窗口传话。用户询问“开始了吗/咋样了”时，先取实时快照，再回答岗位、阶段、通过项和阻断项。
6. 同一文件族始终只有一个写入岗位。审计、浏览器QA和视觉验收默认只读；若写入岗仍在运行，不得再创建第二个写入岗。后续修复通过续派当前写入任务或等待其交回后创建下一棒。
7. 岗位模型与推理档位必须遵守 `MODEL_ROUTING.md`。任务提示必须显式写出岗位、工作包、模型、档位、允许范围、禁止范围、验收标准和停止条件；不得为了显得“效率高”无证据使用 Sol high，也不得临时改掉用户已经确认的组织结构。
8. QA不得以 `toast`、公告、`ACTIVE_RESULT`、事件已写入、按钮可点击或静态脚本 PASS 代替真实机制验收。涉及伤害、控制、位移、掉落、目标选择或范围时，必须验证权威状态变化、最终运行画面、失败分支、到期清理以及DOM重建后仍然正确。
9. “独立版已同步”必须以重新运行构建、构建时间/哈希或内容检查为证据。看到旧画面时先判断源文件缺失、独立版未重建、浏览器缓存或用户打开旧文件，不能未经检查把问题归咎于“版本不对”。
10. 用户明确提出的旧需求若在当前交付中缺失，登记为回归缺陷而非新需求；直接进入复现和派修，不要求用户再次证明或重新整理。
11. 总控发现自己违反以上规则时，必须立即承认具体调度错误、纠正任务形态并保留正在进行的安全改动；不得用流程解释掩盖问题，也不得在没有修正动作时只道歉。
12. 当前阶段只有在唯一写入岗完成、独立只读岗位复测通过、必要门禁通过且连续两轮扩展检查无新增阻断后，才允许向用户说“搞好了”或“可交付”。
